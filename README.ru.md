Панель управления прокси — единый веб-интерфейс + REST API, построен на FastAPI и React. Та же архитектура, что и у PasarGuard (бэкенд на Python/FastAPI, дашборд на React, развёртывание через Docker), но с полностью оригинальным интерфейсом и процессом первого запуска. Поддерживаемые протоколы: **VLESS, Trojan, WireGuard, Hysteria2** (без VMess и Shadowsocks).

## Что уже реализовано

- **Бэкенд** (`backend/`): FastAPI + SQLAlchemy (асинхронный, по умолчанию SQLite), JWT-авторизация, миграции Alembic.
- **Фронтенд** (`frontend/`): React + Vite + Tailwind, визуальное направление «Obsidian Glow», двуязычная (fa/en) страница входа.
- **Пользователи**: создание/список/включение-отключение/удаление прокси-пользователей, с лимитом трафика и отслеживанием реального потребления, а также автоматический переход в статус `истёк`/`ограничен` при превышении даты истечения или лимита данных.
- **Хосты**: эндпоинты VLESS/Trojan/WireGuard/Hysteria2. Для VLESS/Trojan выбирается транспорт (tcp/ws/grpc) и безопасность (none/tls/reality); хосты WireGuard получают свою пару ключей сервера и подсеть туннеля.
- **Группы**: реальный контроль доступа, а не просто организация — хост без группы виден всем пользователям, но как только он попадает в группу, видеть и использовать его могут только пользователи этой же группы. Это правило действует как при генерации ссылок, так и в реальном конфиге Xray, отправляемом на ноды.
- **Сканер REALITY**: тестирует задержку у ~160 доменов-кандидатов и рекомендует самый быстрый в качестве цели REALITY прямо из формы хостов.
- **Ссылки подписки**: каждый пользователь получает ссылку `vless://`/`trojan://`/`hysteria2://` на каждый хост, файл `.conf` для WireGuard на каждый WireGuard-хост (с собственным ключом и IP, выделяемыми при первом обращении), плюс одну ссылку подписки (`/sub/<secret>`, без авторизации админа — клиентские приложения обращаются к ней напрямую) с QR-кодом.
- **Ноды**: регистрируете сервер, получаете команду `docker run` для запуска агента ноды на нём, затем нажимаете «синхронизировать», чтобы отправить сгенерированный конфиг Xray и увидеть статус **подключено** вместе с версией Xray. После этого состояние проверяется автоматически, а реальный трафик каждого пользователя периодически считывается из собственного API статистики Xray. См. раздел [Ноды и агент ноды](#ноды-и-агент-ноды) ниже о том, что именно делает этот агент и каковы его текущие ограничения.
- **Настройки**: изменение публичного URL панели и пароля администратора «на лету», плюс резервное копирование/восстановление базы данных в один клик — всё прямо из дашборда, без передеплоя.
- **Docker**: `docker-compose.yml` поднимает панель + дашборд. Агент ноды (`backend/node_agent/`) собирается и запускается отдельно, по одному на каждую ноду — см. ниже.

Пока не реализовано: разграничение прав между администраторами, управление интерфейсом WireGuard на стороне ноды (`wg-quick`) — полный список и несколько более крупных идей, которые сейчас рассматриваются, см. в `ROADMAP.md`.

## Быстрая установка

**Панель** (сервер, на котором будут работать дашборд и API):
```bash
bash -c "$(curl -fsSL https://raw.githubusercontent.com/javadtifusi-eng/Tifusi-Panel/main/install.sh)"
```
Устанавливает Docker автоматически, если его нет (официальным скриптом `get.docker.com`), клонирует репозиторий, при желании получает бесплатный сертификат Let's Encrypt, если у вас есть домен, указывающий на этот сервер (тогда панель сразу отдаёт HTTPS, без обратного прокси), и поднимает панель через Docker Compose. Учётная запись администратора создаётся потом, из браузера на странице входа — весь процесс описан ниже.

**Нода** (любой сервер, который будет реально запускать Xray-core — сначала создайте ноду на странице «Ноды» панели, чтобы получить её API-ключ):
```bash
bash -c "$(curl -fsSL https://raw.githubusercontent.com/javadtifusi-eng/Tifusi-Panel/main/install-node.sh)" -- <API_KEY> [PORT]
```
Собирает и запускает только агент ноды — ни полной панели, ни базы данных, ничего лишнего на этой машине.

Оба скрипта сначала проверяют наличие Docker и, если его нет, устанавливают его сами официальным скриптом `get.docker.com`.

## Процесс первого запуска (вручную / без install.sh)

Вместо того чтобы отправлять вас в документацию за нужной командой, страница входа показывает её прямо на месте, с кнопкой копирования:

1. Запустите стек: `docker compose up -d`
2. Откройте панель — поскольку администратора ещё нет, отобразится карточка **первоначальной настройки** с кнопкой, которая копирует нужную команду (наведите курсор, чтобы увидеть саму команду).
3. Выполните скопированную команду в терминале вашего сервера:
   ```bash
   docker exec -it tifusi-panel tifusi-cli generate-admin-key
   ```
4. Вставьте выведенный ключ обратно в ту же карточку, выберите имя пользователя/пароль — и учётная запись владельца-администратора будет создана: без отдельной страницы, без необходимости покидать браузер.

Скрипт `install.sh` выше выполняет за вас шаг 1; дальше шаги 2–4 пройдите в браузере.

## Ноды и агент ноды

Нода — это сервер, на котором реально работает Xray-core. `backend/node_agent/` — небольшой сервис на FastAPI, предназначенный для запуска на этом сервере: панель отправляет сгенерированный конфиг Xray POST-запросом на его эндпоинт `/config` (с авторизацией по индивидуальному API-ключу ноды), он (пере)запускает `xray run -config ...` и сообщает о своём состоянии через `/health`.

```bash
docker build -t tifusi-node-agent -f backend/node_agent/Dockerfile backend
docker run -d --name tifusi-node --restart unless-stopped \
  -p 62050:62050 -e TIFUSI_NODE_API_KEY=<из кнопки «команда установки» в панели> \
  tifusi-node-agent
```

Dockerfile этого агента ноды при сборке скачивает настоящий бинарник Xray-core из его релизов на GitHub — этот шаг не удалось проверить в изолированной среде (sandbox), в которой создавался этот проект (исходящий доступ к GitHub там был заблокирован), поэтому **соберите и запустите его на настоящей машине, прежде чем доверять ему в продакшене**. Всё остальное (генерация конфига, HTTP-контракт между панелью и агентом, отчёты о статусе) было полностью проверено там же с использованием подставного бинарника.

В сам конфиг Xray попадают только хосты VLESS и Trojan — Hysteria2 вообще не является частью Xray-core (это отдельный сервер), а WireGuard — это дело уровня ядра/`wg-quick`, и ни то ни другое этот агент не запускает. Оба протокола просто пропускаются здесь, вместо того чтобы получить нерабочий inbound; WireGuard по-прежнему полностью поддерживается на уровне генерации ссылок (см. выше), просто не этим агентом ноды.

## Локальная разработка

**Бэкенд**
```bash
cd backend
pip install -r requirements.txt
uvicorn app.main:app --reload
```

**Фронтенд**
```bash
cd frontend
npm install
npm run dev
```
Dev-сервер Vite проксирует `/api` на `http://localhost:8000`.

**Сгенерировать ключ установки без Docker**
```bash
cd backend
python -m cli.main generate-admin-key
```

## Миграции базы данных

Изменения схемы проходят через Alembic (`backend/alembic/`), а не через `Base.metadata.create_all()` — приложение автоматически выполняет `alembic upgrade head` при каждом запуске (`app/migrate.py`, вызывается из `init_db()`), поэтому обычный деплой всегда приводит к последней схеме без ручного шага и без необходимости удалять базу данных.

При изменении модели создайте миграцию и закоммитьте её вместе с изменением модели:
```bash
cd backend
alembic revision --autogenerate -m "описание изменения"
```
Всегда просматривайте сгенерированный файл перед коммитом — autogenerate даёт хороший черновик, но не гарантию, особенно для того, с чем SQLite работает неуклюже (например, изменение существующего столбца может потребовать `op.batch_alter_table(...)`).

## Развёртывание через Docker

```bash
cp .env.example .env   # укажите настоящий TIFUSI_SECRET_KEY, и TIFUSI_PUBLIC_URL, если панель за прокси
docker compose up -d --build
```

- API панели: `http://localhost:8000`
- Дашборд: `http://localhost:8080`
- Данные SQLite сохраняются в `./data`

Задайте `TIFUSI_PUBLIC_URL` (например, `https://your-domain.example`), когда панель работает за Docker/прокси — без этого ссылки подписки строятся из заголовка Host запроса, а это там внутренний хостнейм контейнера, недоступный клиенту. Эта переменная окружения — лишь начальное значение по умолчанию: администратор может в любой момент посмотреть и изменить её прямо со страницы настроек панели (там же меняется и пароль администратора), без передеплоя.

### HTTPS на дашборде (рекомендуется, отдельный обратный прокси не нужен)

Контейнер `dashboard` (тот, что вы реально открываете в браузере) может сам завершать TLS на порту 443 и проксировать `/api/` и `/sub/` на панель внутри сети — именно это настраивает за вас шаг с доменом/Let's Encrypt в `install.sh`. Ещё два способа включить это без переустановки:

- **Прямо из панели**: Настройки → Сертификат SSL → загрузите `fullchain.pem`/`privkey.pem`. Заработает примерно через 15 секунд, перезапуск не нужен.
- **Вручную**: положите `fullchain.pem`/`privkey.pem` в `./certs` на сервере и перезапустите (`./certs` уже смонтирован в оба контейнера).

В обоих случаях `./certs` постоянно отслеживается — контейнер сам обнаруживает новый (или удалённый) сертификат и перезагружает nginx, без правки `nginx.conf` или ручного перезапуска.

### Прямой TLS на панели (продвинутый вариант, без дашборда/прокси перед ней)

По умолчанию контейнер панели работает по обычному HTTP внутри сети — наружу должен смотреть именно nginx дашборда (см. выше). Если вы вообще не используете контейнер dashboard и хотите, чтобы TLS для прямого доступа к API завершал сам uvicorn:

```bash
# в .env
TIFUSI_SSL_CERTFILE=/app/certs/fullchain.pem
TIFUSI_SSL_KEYFILE=/app/certs/privkey.pem
```

и смонтируйте свои сертификаты в контейнер (раскомментируйте строку `./certs:/app/certs:ro` в `docker-compose.yml`). Точка входа контейнера (`run.py`) подхватывает их автоматически — больше ничего не меняется. Обе переменные должны быть заданы вместе, либо ни одна из них; если задать только одну, приложение сразу завершится с ошибкой при запуске вместо того, чтобы незаметно откатиться на HTTP.
