# مدیریت و عملیات

## فرمان مدیریت

فرمان `tifusi panel` بدون آرگومان یک منوی تعاملی و با آرگومان یک عملیات مشخص را اجرا می‌کند:

| فرمان | عملیات |
| --- | --- |
| `tifusi panel update` | به‌روزرسانی به آخرین نسخه و ساخت دوباره‌ی کانتینرها |
| `tifusi panel status` | نمایش وضعیت کانتینرها |
| `tifusi panel logs` | دنبال کردن لاگ کانتینرها |
| `tifusi panel restart` | راه‌اندازی دوباره‌ی مجموعه |
| `tifusi panel port` | تغییر پورت‌های API پنل و داشبورد |
| `tifusi panel ssl` | صدور گواهی Let's Encrypt |
| `tifusi panel key` | تولید کلید راه‌اندازی جدید برای مدیر |
| `tifusi panel backup` / `tifusi panel restore` | پشتیبان‌گیری یا بازیابی پایگاه داده |
| `tifusi panel uninstall` | حذف نصب |

فرمان `tifusi` یک راه‌انداز مشترک با [Tifusi Bot](telegram-bot.md) است: `tifusi bot` منوی نصب‌کننده‌ی ربات را باز می‌کند. اگر روی سرور تنها یکی از پنل یا ربات نصب باشد، `tifusi` بدون زیرفرمان همان را باز می‌کند؛ از این رو `tifusi update` همچنان کار می‌کند.

سرورهای نود منوی `tifusi node` مخصوص خود را دارند؛ بخش [نودها](nodes.md) را ببینید.

## آپدیت بدون غافلگیری

ایجنت نودها و باینری تانل‌ها از داخل پنل با برگشت خودکار آپدیت می‌شوند — نودها یکی‌یکی با Canary، تانل‌ها هر سمت جدا — و هر کانفیگی که به نود فرستاده می‌شود قبل از جایگزین شدن اعتبارسنجی می‌شود. اینکه هر لایه چطور بررسی می‌کند و برمی‌گردد در [به‌روزرسانی امن](updates-and-rollback.md) آمده است.

## مدیران

پنل یک حساب مالک و هر تعداد مدیر اضافی با مجوزهای محدود روی کاربران، هاست‌ها، نودها، هسته‌ها، گروه‌ها، تانل‌ها و تنظیمات دارد. مدیر محدود فقط کاربرانی را می‌بیند که خود ساخته است. هر مدیر می‌تواند برای خودکارسازی کلید API صادر کند؛ کلید همیشه مجوزهای فعلی صاحبش را دارد. تغییر رمز عبور همه‌ی کلیدهای API خودتان را باطل می‌کند، مگر گزینه‌ی **همه‌ی کلیدهای API من هم باطل بشن** را بردارید (در API: `"revoke_api_keys": false`). [نمایندگان](resellers.md) نوع جداگانه و محدودتری از حساب هستند.

## ورود به پنل

جدا از رمز عبور (با کد دومرحله‌ای اختیاری از اپ Authenticator)، مدیر می‌تواند با **گوگل** یا **گیت‌هاب** وارد شود:

- **مالک، یک بار:** برای آدرس همین پنل یک اپ OAuth نزد سرویس‌دهنده بسازد و Client ID و Client Secret آن را در **تنظیمات ← ورود با گوگل و گیت‌هاب** وارد کند. همان بخش آدرس بازگشت دقیقی را که باید ثبت شود نشان می‌دهد (`https://<panel>/api/auth/oauth/google/callback` یا `/github/callback`). Secret فقط روی سرور می‌ماند و دیگر نمایش داده نمی‌شود؛ اگر هیچ‌کدام تنظیم نشود، صفحه‌ی ورود مثل قبل است.
- **هر مدیر:** حساب خودش را از همان بخش، با تأیید رمز فعلی پنل، وصل می‌کند و از آن به بعد با دکمه‌ی صفحه‌ی ورود وارد می‌شود. فقط حساب‌های وصل‌شده اجازه‌ی ورود دارند: حساب گوگل یا گیت‌هابی که کسی وصلش نکرده رد می‌شود و هر حساب حداکثر به یک مدیر وصل می‌شود. اگر ورود دومرحله‌ای روشن باشد، بعد از سرویس‌دهنده هم کدش پرسیده می‌شود.
- **مرا به خاطر بسپار** در صفحه‌ی ورود، آن مرورگر را به‌جای یک روز تا ۳۰ روز وارد نگه می‌دارد؛ بدون آن، با بستن مرورگر هم ورود تمام می‌شود.
- **خروج از همه‌ی دستگاه‌ها** همه‌ی ورودهای آن مدیر را، حتی به‌خاطرسپرده‌ها، همان لحظه باطل می‌کند. تغییر رمز هم همین کار را می‌کند و حساب‌های گوگل و گیت‌هاب وصل‌شده را هم جدا می‌کند (کسی که رمز قبلی را داشته ممکن است حساب خودش را وصل کرده باشد)؛ بعدش دوباره وصلشان کنید.

رمز عبور همیشه کار می‌کند، پس از دست دادن دسترسی به گوگل یا گیت‌هاب کسی را بیرون نمی‌گذارد.

## اعلان‌ها

تغییر وضعیت کاربران و نودها، رویدادهای [سپر اتصال](connection-shield.md) و سوختن و برگشتن دامنه‌ها در [چرخش دامنه](domain-rotation.md) را می‌توان به تلگرام، دیسکورد یا یک webhook عمومی ارسال کرد. رویدادهای سپر در webhook با نام‌های `shield_burnt`، `shield_switched`، `shield_no_spare`، `shield_recovered` و `shield_error` می‌رسند. بعد از هر آپدیت پنل، نود یا تانل هم یک [گزارش کوتاه](updates-and-rollback.md#گزارش-آپدیت-در-تلگرام) به تلگرام می‌رود.

## تنظیمات

نشانی عمومی، رمز مدیر، گواهی TLS (بارگذاری یا صدور Let's Encrypt) و پشتیبان‌گیری و بازیابی پایگاه داده همگی از بخش **تنظیمات** تغییر می‌کنند و بدون استقرار دوباره اعمال می‌شوند. پشتیبان‌گیری بخش تنظیمات برای نسخه‌ی عادی است؛ در نسخه‌ی حرفه‌ای از `tifusi panel backup` استفاده کنید که خروجی MySQL را هم شامل می‌شود.
